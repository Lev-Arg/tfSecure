# Passcode Access Control System — Development Spec

## 1. Overview

A single-use passphrase system for managing visitor, contractor, and
vendor access to premises. Passphrases are generated by the system,
pooled per department, assigned by department heads to expected
visitors, and validated at the gate by security. Every passphrase is
used exactly once and is never recycled.

**Flow in brief:**
System generates passphrases per department → given to department heads
only → head assigns one to an expected visitor for a meeting/appointment
(visitor details auto-captured in the system) → host relays the
passphrase to the visitor via whichever channel they normally use → gate
security validates the passphrase on arrival → access granted/denied →
passphrase invalidated the moment the visitor exits → unused passphrases
die at 23:00 same day → never reusable, ever.

---

## 2. Actors

| Actor | Capabilities |
|---|---|
| **System (automated)** | Generates passphrases, replenishes pools, auto-expires unused passphrases, fires overstay alerts |
| **Security Admin** | Configures pool thresholds, resolves overstay alerts, manual void, views all logs |
| **Department Head** | Logs in, views own department's unassigned passphrases, assigns one to a visitor, views status of passphrases they assigned |
| **Gate Security (guard)** | Enters/hears passphrase, checks visitor in/out |
| **Visitor/Contractor/Vendor** | Receives passphrase from host out-of-band (call/SMS/WhatsApp/email/in person — host's choice), presents it at gate |

## 3. Core Entities

```
Department {
  id: UUID
  name: string
  min_pool_threshold: int      // triggers on-demand replenishment
  active: boolean
}
```

  id: UUID

```

```
Passcode {
  id: UUID
  code: string                   // e.g. "PROCURE-MANGO", unique, non-guessable
  department_id: FK -> Department
  batch_id: FK -> GenerationBatch
  state: enum [
    UNASSIGNED,
    ASSIGNED,
    ACTIVE,
    OVERSTAY_ALERT,
    USED,
    EXPIRED,
    VOID
  ]
  generated_at: timestamp
  assigned_at: timestamp | null
  checked_in_at: timestamp | null
  checked_out_at: timestamp | null
  expires_at: timestamp | null   // set to 23:00 of assignment day
  assigned_by: FK -> DepartmentHead | null
  visitor_id: FK -> Visitor | null
}
```

### 3.4 Visitor
```
Visitor {
  id: UUID
  full_name: string
  phone: string
  company: string | null
  id_document_ref: string | null   // e.g. ID/passport number
  purpose: string
  host_name: string
  appointment_time: timestamp
  passcode_id: FK -> Passcode
}
```

### 3.5 GenerationBatch
```
GenerationBatch {
  id: UUID
  department_id: FK -> Department
  triggered_by: enum [SCHEDULED_0400, ON_DEMAND]
  requested_by: FK -> DepartmentHead | null   // null if scheduled
  quantity: int

```

```
AuditLog {
  id: UUID

```
OverstayAlert {
  id: UUID

  resolved_by: FK -> DepartmentHead | null   // SECURITY_ADMIN role

}
```

## 4. State Machine

```
UNASSIGNED --(head assigns to visitor)--> ASSIGNED
ASSIGNED --(gate check-in)--> ACTIVE
ASSIGNED --(23:00, never checked in)--> EXPIRED
ACTIVE --(gate check-out)--> USED
ACTIVE --(23:00, never checked out)--> OVERSTAY_ALERT
OVERSTAY_ALERT --(security confirms departure)--> USED
OVERSTAY_ALERT --(security escalates)--> VOID
[any pre-ACTIVE state] --(manual revoke)--> VOID
```

**Terminal states:** `USED`, `EXPIRED`, `VOID` — passphrases never leave
these states and are never returned to a pool. Nothing is ever reused.

---

## 5. Scheduled Jobs

| Job | Time | Behavior |
|---|---|---|
| **Replenishment** | 04:00 daily | For each department, if `UNASSIGNED` count < `min_pool_threshold`, generate a new batch to top up. Logs a `GenerationBatch`. |
| **Daily expiry sweep** | 23:00 daily | For each `ASSIGNED` passphrase not yet checked in → set `EXPIRED`. For each `ACTIVE` passphrase not yet checked out → set `OVERSTAY_ALERT` and notify security + host (do NOT void — a person may still be on-site). |

**On-demand replenishment:** a department head or security admin can
trigger a batch generation immediately if `UNASSIGNED` count hits 0,
independent of the 04:00 job. Rate-limited to prevent abuse (e.g. max N
manual requests per department per day).

## 7. Validation Logic (Gate Check)

```
On /gate/validate(code):
  lookup Passcode by code (case-insensitive match)
  if not found            -> DENY: "invalid passphrase"
  if state == UNASSIGNED  -> DENY: "not assigned to any visitor"
  if state == EXPIRED     -> DENY: "passphrase expired"
  if state == VOID        -> DENY: "passphrase revoked"
  if state == USED        -> DENY: "passphrase already used — not reusable"
  if state == ACTIVE      -> DENY: "already checked in, not checked out"
                              (flag possible duplicate/lost-passphrase scenario)
  if state == ASSIGNED
      and now > expires_at -> auto-flip to EXPIRED, DENY
  if state == ASSIGNED
      and now <= expires_at -> ALLOW: proceed to check-in
```

## 8. Passphrase Format & Distribution

- **Format:** two-word &three-word passphrase, randomly paired from curated word
  lists — e.g. `PROCURE-MANGO-LOVE`, `PINK-OCTOPUS-ARENA`, `STINGY-GOAT`,
  `HEAD-LIGHT`. Easier for hosts to read aloud/text, and for guards to
  key in, than an alphanumeric string — while still effectively random
  and non-sequential.
  - Draw each half from a fixed word list (e.g. 500+ words each) so the
    combination space is large enough to resist guessing (500 x 500 =
    250,000 combos per list pair; scale list size to expected daily
    volume and acceptable collision risk).
  - Words must be unrelated to department names — a passphrase should
    **not** reveal which department/area it grants access to. The
    department link lives only in `department_id` on the Passcode
    record, looked up server-side.
  - Pre-filter word lists for accidental real-word collisions or
    inappropriate combinations.
  - Case-insensitive matching at the gate.
- **Distribution:** the system does not message the visitor directly.
  Once a head assigns a passphrase, the **host relays it to the visitor
  via whichever channel they'd normally use** — phone call, SMS,
  WhatsApp, email, or in person. This keeps the system agnostic to the
  visitor's preferred contact method and puts the human touch where it
  belongs, with the host.

## 9. Security & Access Control

- **Department isolation:** a head's session can only query/mutate
  passphrases where `department_id == head.department_id`. Enforce at
  query layer, not just UI.
- **MFA** recommended for department head and security admin logins
  given physical access is at stake.
- **Rate limiting** on `/gate/validate` to prevent brute-force guessing.
- **Immutable audit log** — every state transition writes an AuditLog
  row; logs are append-only (no update/delete).
- **PII handling** — visitor ID document numbers, phone numbers:
  encrypt at rest, restrict read access to security admin + the
  assigning head only.

## 10. Notifications

| Event | Recipient(s) | Channel |
|---|---|---|
| Passphrase assigned | Visitor — host relays it directly, via whichever channel they normally use with that visitor | Host's choice — outside system scope |
| Overstay alert raised (23:00) | Security Admin, assigning Dept Head | Push/SMS/Dashboard alert |
| Pool below threshold, on-demand batch requested | Security Admin | Dashboard/Email |
| Passphrase expired unused | Assigning Dept Head (informational) | Dashboard |

## 11. Open Implementation Decisions (flag before build)

1. Exact word-list size/source and entropy requirement.
2. Multi-day passes (e.g. contractor working a week) — out of current
   scope (spec assumes single-day validity); if needed, treat as N
   sequential single-day passphrases rather than one persistent code.
3. Physical gate hardware integration (kiosk, RFID, QR alongside spoken
   passphrase) vs. manual guard entry only.
4. Timezone handling — confirm all "23:00" and "04:00" cutoffs use
   premises local time, DST-aware.

---

## 12. Suggested Stack 

- **Backend:** Node.js/Express or Django — either fine; needs solid cron
  support (node-cron / Celery beat) for the 04:00 and 23:00 jobs.
- **DB:** PostgreSQL (relational integrity for state machine + FKs
  matters more than flexibility here).
- **Auth:** JWT sessions + TOTP-based MFA.
- **Gate terminal:** lightweight web app or dedicated kiosk client
  hitting `/gate/*` endpoints; should work offline-tolerant if network
  drops (queue and sync) — flag as a decision if premises has spotty
  connectivity. #there's a LAN and a Wi-Fi that every office is connected to.
